# PR-3 production deploy — двухфазная модель (Phase A / Phase B)

Операторский справочник по `scripts/deploy_pr3.sh`. Описывает, **почему** деплой
разделён на две фазы, какие ревизии входят в аудированный catch-up и в каком
состоянии остаётся база после каждого типа отказа.

Связанные документы:

- `docs/easyweek/pr3_production_dump_rehearsal.md` — репетиция upgrade/downgrade
  на копии production dump (обязательный DoD PR-3).
- `.github/workflows/ci_deploy.yml` — workflow, который фетчит точный commit и
  передаёт управление в `scripts/deploy_pr3.sh`.
- `src/altegio_bot/tests/test_pr3_migration_catchup.py` — исполняемые гарантии
  всего, что описано ниже.

---

## 0. Жёсткие запреты

- Не выполнять `downgrade` на production вручную.
- Не выполнять `alembic stamp` и не править `alembic_version` руками, чтобы
  «починить» классификацию. Деплой сознательно падает fail-closed вместо того,
  чтобы записать в базу удобное значение.
- Не заменять Phase A на `alembic upgrade head`: head — это PR-3, и его
  применение при живом старом worker'е и есть та авария, ради предотвращения
  которой существует Phase B.

---

## 1. Почему фаз две

PR-3 (`c1a7d3f905b2`) меняет уникальные constraint'ы на provider-scoped:

```text
uq_clients_company_altegio_id  → uq_clients_provider_company_altegio_id
uq_records_company_altegio_id  → uq_records_provider_company_altegio_id
```

Запущенный inbox-worker **предыдущего** релиза ссылается на старые имена в
`ON CONFLICT ON CONSTRAINT`. Если он продолжит работать во время замены, каждое
обработанное в этом окне событие упадёт на отсутствующем constraint и осядет со
статусом `failed`, а `failed` никто не ретраит. Поэтому PR-3 применяется только
в окне с остановленным worker'ом (Phase B) и с проверкой canary после.

Обычные же миграции такого окна не требуют: они аддитивны и старый код их просто
не замечает. Раньше это различие не было выражено в коде — деплой требовал, чтобы
база стояла **ровно** на `9a1f4c7b2e3d`, и отказывался работать, если production
отставал на несколько обычных ревизий. Phase A закрывает именно этот пробел.

## 2. Аудированный catch-up path

Phase A применяет строго эту цепочку, от текущей ревизии до `9a1f4c7b2e3d`:

```text
b7c8d9e0f1a2  →  c9d0e1f2a3b4  →  d0e1f2a3b4c5  →  d8f6e4c2b1a0
              →  e9a7c6b5d4f3  →  8923be993170  →  8705ec49cc73
              →  9a1f4c7b2e3d
```

Затем Phase B делает ровно один шаг:

```text
9a1f4c7b2e3d  →  c1a7d3f905b2
```

Результат аудита каждой ревизии:

| Ревизия | Что делает | Аддитивна | Идемпотентна | Совместима со старым runtime |
| --- | --- | --- | --- | --- |
| `b7c8d9e0f1a2` | расширяет CHECK `ck_promo_leads_status` (добавляет `pending_check`) | да (расширение) | нет¹ | да — старый код пишет только прежние статусы |
| `c9d0e1f2a3b4` | +5 nullable колонок, +5 индексов, backfill из JSONB | да | да | да — старый код колонок не знает |
| `d0e1f2a3b4c5` | +1 partial composite index | да | да | да |
| `d8f6e4c2b1a0` | `CREATE TABLE meta_circuit_breaker` | да | да | да — новая таблица |
| `e9a7c6b5d4f3` | +3 nullable колонки в `meta_circuit_breaker` | да | да | да |
| `8923be993170` | `CREATE TABLE easyweek_events` + 4 индекса | да | да | да — новая таблица |
| `8705ec49cc73` | +2 колонки в `easyweek_events` | да | да | да |
| `9a1f4c7b2e3d` | +2 nullable колонки, guarded FK, partial unique index | да | да | да — partial index покрывает только non-NULL |

¹ `b7c8d9e0f1a2` использует `drop_constraint` без `IF EXISTS`, поэтому повторный
запуск самого файла упал бы. Alembic никогда не переприменяет уже применённую
ревизию, так что для деплоя это безопасно; отмечено ради полноты.

**Ключевое свойство всей цепочки:** ни одна из этих ревизий не переименовывает и
не удаляет constraint, на который старый worker ссылается по имени. Единственный
затронутый constraint — CHECK `ck_promo_leads_status`, и он **расширяется**, то
есть все записи старого кода остаются валидными. Это и есть причина, по которой
Phase A выполняется при работающем старом runtime, а Phase B — нет.

Ревизия вне этого списка **не** применяется автоматически: деплой падает
fail-closed и требует ручного аудита.

## 3. State machine деплоя

```text
   verify DEPLOY_SHA
        ↓
   build images
        ↓
   postgres healthy  →  SELECT 1  →  pg_dump (обязательный непустой backup)
        ↓
   прочитать ревизию через alembic_revision()
        ├─ не резолвится ────────────────→ FAIL CLOSED (ничего не тронуто)
        ↓
   классификация по реальному графу ScriptDirectory
        ├─ PR-3 уже в lineage БД ────────→ обычный идемпотентный deploy
        ├─ PR-3 не в графе ──────────────→ обычный deploy
        ├─ ревизия == 9a1f4c7b2e3d ──────→ Phase B
        ├─ ревизия на аудированном пути ─→ Phase A, затем Phase B
        └─ иначе ────────────────────────→ FAIL CLOSED
        ↓
   ┌── Phase A (старый worker РАБОТАЕТ) ──────────────────┐
   │  alembic upgrade 9a1f4c7b2e3d   (не head)            │
   │  перечитать ревизию                                  │
   │  ревизия != 9a1f4c7b2e3d → FAIL CLOSED               │
   │  ничего не остановлено, статусы событий не тронуты   │
   └──────────────────────────────────────────────────────┘
        ↓  только при точном совпадении DB == 9a1f4c7b2e3d
   ┌── Phase B (окно с остановленным worker'ом) ──────────┐
   │  deploy boundary из PostgreSQL                       │
   │  stop legacy inbox worker  →  drain verification     │
   │  bounded recovery: processing → received             │
   │  alembic upgrade c1a7d3f905b2                        │
   │  canary на новом образе  →  verification             │
   │  recreate regular worker →  verification             │
   │  retire canary                                       │
   └──────────────────────────────────────────────────────┘
        ↓
   compose up -d --remove-orphans, followup/Chatwoot checks
```

`altegio-api` **не** останавливается ни в одной фазе: вебхуки продолжают
приниматься и копятся как `received`.

## 4. Повторный деплой и partial catch-up

Phase A возобновляема. Если она упала посередине — часть ревизий уже применена,
и база стоит на промежуточной ревизии аудированного пути. Повторный деплой:

- снова прочитает ревизию,
- увидит её на аудированном пути,
- вычислит оставшийся хвост и достроит его до `9a1f4c7b2e3d`,
- затем выполнит Phase B.

Перед применением деплой сверяет путь, который Alembic посчитал **фактически**, с
аудированным хвостом. Если в цепочку добавили новую ревизию, строки не совпадут и
деплой остановится, а не применит неаудированный DDL.

## 5. Состояние базы после каждого отказа

| Сценарий | Ревизия после отказа | Worker | Очередь |
| --- | --- | --- | --- |
| Ревизия не резолвится | без изменений | работает | не тронута |
| Ревизия вне аудированного пути | без изменений | работает | не тронута |
| Фактический путь ≠ аудированному | без изменений | работает | не тронута |
| **Phase A упала** | промежуточная ревизия пути; **откат не выполняется** | работает, не останавливался | не тронута |
| Phase A прошла, Phase B упала до canary | `9a1f4c7b2e3d` — catch-up сохранён | возвращается прежний worker | bounded recovery |
| Phase B упала после verified canary | `c1a7d3f905b2` | canary оставлен работать | bounded recovery |
| Phase B упала после verified regular worker | `c1a7d3f905b2` — **downgrade запрещён** | regular worker | bounded recovery |

### Почему Phase A не откатывается автоматически

Все ревизии catch-up аддитивны и совместимы со старым кодом. Откат означал бы
удаление таблиц и колонок, которые:

- ничего не ломают, оставаясь на месте;
- могут уже содержать данные, записанные новым кодом;
- будут нужны при следующей же попытке деплоя.

Поэтому автоматический откат ограничен **только** заменой constraint'ов PR-3:

```text
c1a7d3f905b2  →  9a1f4c7b2e3d
```

После такого recovery production остаётся на `9a1f4c7b2e3d`. **Это ожидаемое
состояние, а не незавершённый откат.** Автоматический откат catch-up до более
ранней ревизии не выполняется никогда.

## 6. Если ревизия не резолвится

Симптом:

```text
❌ Alembic could not resolve the revision recorded in this database.
```

Значит `alembic_version` содержит идентификатор, которого нет в графе этого кода.
Alembic в таком состоянии не может вычислить **никакой** путь — ни catch-up, ни
обычный upgrade.

Диагностика (только чтение):

```bash
docker compose -p altegio_bot exec -T postgres sh -lc 'psql -tAX -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version_num FROM alembic_version"'
```

```bash
uv run alembic history --verbose
```

Дальше — вопрос идентичности базы: восстановленный дамп из другого окружения,
ревизия с невлитой ветки, ручной `stamp`. Решение принимает человек. Деплой
сознательно не «чинит» это сам: любой автоматический `stamp` записал бы в
`alembic_version` значение, не соответствующее фактической схеме.

> Историческая заметка. `alembic current` печатает текст ошибки
> `FAILED: Can't locate revision identified by '<id>'` в **stdout**, и в нём есть
> 12-символьный hex. Прежний ридер брал первый такой токен, не проверив код
> возврата, из-за чего идентификатор из **сообщения об ошибке** попадал в лог как
> будто это реальная ревизия базы. Теперь код возврата проверяется первым, и
> принимается только «голый» id в начале строки.
